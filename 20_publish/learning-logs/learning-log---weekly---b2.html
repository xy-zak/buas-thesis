Progress:

-> Meeting dates with my first & second reader are agreed, and the block plan has gone to my first reader.
-> The data minimum requirements are done, in two versions. The first draft (v1, 11-11) lists 13 kinds of data, split into necessary (without it a sub-question cannot be answered) and additional (it explains, checks or strengthens an answer), with a table showing which sub-question each one serves. Every record carries the same tags (group, condition, round, seat and a timestamp), so the logs can be joined up later.
-> I then re-analysed it (v2, 18-11) against my literature review, the research question dissection, the ILO rubric, the Block B brief, and my time and budget, always preferring the simpler design. The main results:
> Discussion means proposals. For now, the proposal tool in the game is the only way players talk during play, so there are no recordings. My introduction already says the study traces “who proposes what and who acts on it, rather than what is said”.
> Six necessary records, all from the game log: the session and condition, the knowledge map (starting scores), proposals, decisions, resource health per round, and private scores per round.
> Four cheap extras: a one-item manipulation check, miniPXI after each condition, three background questions, and my session notes.
> Floor and ceiling simulations in both conditions: agents that never propose, and agents that know everything. Every group’s result is read as a position between the two.
> miniPXI (the 11-item short form of the Player Experience Inventory) measures how each condition feels to play. Autonomy is the one item chosen in advance for testing, and the rest are reported descriptively.
> Four sub-questions, not five: SQ5 (the links) is dropped, matching the introduction.
> Dropped: recordings (for now), trait dominance and the other moderators as analysed variables, and interface telemetry in real sessions. Whether the discussion hub is a person or a position can be read from the log instead, because each player keeps their seat while their knowledge changes between conditions.
> Groups and rounds: 10 groups minimum and 20 as the aim (40-80 players), each playing both conditions, 3 rounds per condition, in a session under 60 minutes.
-> I built the experiment harness, Who Knows, Who Acts?, a week earlier than planned. It is everything around the game, not the game itself:
> Networking: four browsers connect over a local network to one server, my laptop. No internet is needed. The server decides everything and only sends each player what their seat may see, so the knowledge split cannot be got around in the browser.
> The condition: each seat gets a knowledge label (Ka-Kd) and a power label (Pa-Pd). They are either aligned (each player acts where they know) or one of six fully separated pairings, where no seat holds matching letters. Every session records which pairing it used.
> Logging: every action is a permanent event in an append-only log, with server and client timestamps. Interface behaviour is logged too (hovering, inspecting, zooming, confirming, cancelling, idle time), so reaction times can be measured. Every export comes with a generated codebook.
> Data protection: in-game consent (storing a hash of the exact text shown), no logging before consent, random participant codes, names only on a hand-written paper key sheet, an encrypted database, a takedown card for every player, one-step erasure, and anonymised exports for publication.
> Facilitator manager: a ten-step setup, a live dashboard that always shows the next action, a replay of any session, and a database tab. A session runbook explains each step.
> Placeholder rules: a grid map where every square holds four sub-squares, one per knowledge type. Players propose and decide on squares, and a decision changes the scores. The rules live in one file and are versioned, and every event stores the score changes it caused, so changing the rules later never changes data already collected.
> Testing without people: simulated players (software agents that see only what a player would see, are seeded so a run can be repeated exactly, and are stored in a separate database), and fake players that fill empty seats for rehearsals and are marked as fake in the data.
> Accessibility: every screen has its own display settings (high contrast, the OpenDyslexic font, text size, animations on or off). These are never sent to the server, so nothing about a player’s eyesight or dyslexia ends up in the data.
-> The harness has seven design documents: architecture, networking, data management, data types, the session runbook, the visual rules and the game rules. Each one has a change log that records the date, the commit, what changed and why. Every reason is classed as a Feature, a Bug fix or a Risk mitigation. Parts of the documents are generated from the code, and a test fails if they drift apart.
-> The harness can still change the number of rounds, the quotas and the time limits per session, so the pilots can adjust them without new code.
-> The levers will work differently from each other. That is part of the game design for week 3.

Reflection:

-> Building the harness before the game turned out to be the right order. The rules are still open, but what every version of the game needs (networking, logging, consent, data protection) is not. A game idea can now be tried by changing one file, which is why the game ideas moved to week 3 instead of being rushed this week.
-> Putting the harness next to the data requirements shows what is still missing. It already records the session and condition, the starting scores (the knowledge map), proposals, decisions and the scores after each action. It does not yet record a private score per player, proposals aimed at another player’s lever, or which two plays belong to the same group. v2 lists these, and they go into the first full game code in week 4.
-> The talk mode was the most urgent open decision, and the methodology lecture asked the right question about it: what does “discussion” actually mean in my study, and can it be simplified without losing the research question? My own introduction had already answered it. Making proposals the only channel removes recordings, transcription and a coding scheme. It also removes the advantage of fluent English speakers, which the lecture flagged as a way of excluding people. Recording discussion later would not just be a code change: it would change the consent text, the data inventory and the data protection risks, so I want my readers’ view before the code depends on it.
-> My first pass at simplifying also cut the optimiser ceiling, and that was a mistake. A simulation costs no participant time and adds no variables to the experiment, and it gives every group’s result a scale from “no better than silence” to “perfect co-ordination”. “Simpler” should be judged by what reaches the players and the analysis, not by how much code it takes.
-> The real limit is now people, not code. Twenty groups is 80 volunteers with no payment, and at two sessions per Thursday that is 10 Thursdays, more than Block C has. Ten groups is the floor that still answers the question, and that is the number I plan around.
-> I built far more this week than the plan asked for. Most of it was planned for later weeks anyway (consent, agents, logging), so it is pulled forward rather than new. Some of it is new, though (the replay, the visual design, the display settings). In week 1 I warned myself about the methodology note being too big, and a harness can be too big in the same way.
-> The change logs work much like the internal / external notes on my block plan: every change has a date and a reason. They also made this learning log easy to write, since it is mostly a summary of them.

Risks & Mitigations:

-> risk The harness and its documents were built quickly with AI help (Claude Code), so some code or text may not be fully checked by me. mitigation The harness has unit, integration and end-to-end tests (full games, data protection guarantees, documents drifting from the code). I read every change log entry, and I will play full sessions with fake players myself before any pilot. My AI use declaration in the thesis will also cover the game code. Also, this is a similar research harness to what I have built previously in my (job) research projects.
-> risk Proposals as the only way to talk may feel unnatural to players, or my readers may ask for free talk. That would bring back recordings, a coding scheme and changes to consent and data protection. mitigation Check in the paper test whether players can play without talking, and go through the decision with my readers in week 3, before the code depends on it. v2 keeps a fallback: a typed chat that is logged but not coded, reported as a limitation.
-> risk 20 groups means 80 unpaid volunteers, and more session days than Block C has. mitigation Plan around the minimum of 10 groups, keep sessions under 60 minutes, and start listing dates and recruits in Block B, alongside the pilot recruitment.
-> risk Week 3 is now full: paper research, two rounds of game ideas, the talk mode and a paper test. mitigation If the week overflows, the second round of ideas moves to week 4, next to the second paper playtest.
-> risk The harness keeps growing while the game itself is still undecided, the same trap as the oversized methodology note. mitigation No new harness features until the game rules exist. Every new feature has to serve an item on the data requirements list.
-> risk The repository is public, so participant data could leak through a careless commit. mitigation The data and export folders are ignored by Git, and a test checks this. Simulated and fake data are kept separate or marked, so they are never mistaken for participants’ data.
